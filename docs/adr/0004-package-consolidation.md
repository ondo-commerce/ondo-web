# ADR-0004: 공유 패키지를 8개가 아닌 4개로 통합한다

- **Status**: Accepted
- **Date**: 2026-08-03
- **Decider**: Frontend 담당 (단독 결정)
- **관련**: [09 Monorepo 아키텍처](../09-monorepo-architecture.md), ADR-0001

## 맥락

- 모노레포에 앱 2개(B2B 도매몰, B2C 소매몰). 공유 대상은 UI·디자인시스템·API 클라이언트·훅·유틸·타입·ESLint·TS 설정.
- 이걸 그대로 패키지로 매핑하면 **`design-system`, `ui`, `api-client`, `types`, `hooks`, `utils`, `eslint-config`, `typescript-config` 8개**가 된다. Turborepo 공식 예제와 대형 조직 레포에서 흔한 구성이다.
- 그러나 우리 조건은 **주니어 프론트엔드 1명 · 6개월 · 소비자는 앱 2개 · 외부 npm 배포 없음**이다.
- 패키지 경계에는 고정 비용이 있다: `package.json`, `tsconfig`, `exports` 필드, 의존성 그래프 유지, 버전 드리프트 점검, 의존성 업그레이드 시 8곳 확인.
- 그 비용을 정당화하는 이득은 **독립 버저닝 / 독립 배포 / 다른 팀 소유** 세 가지인데, **현재 어느 것도 해당되지 않는다.**

## 결정

**공유 패키지를 4개로 통합한다.**

| 패키지 | 흡수 | 책임 |
|---|---|---|
| `@ondo/ui` | ← `design-system` | 디자인 토큰 + Tailwind preset + 표현 컴포넌트 |
| `@ondo/api` | ← `types` | OpenAPI 생성 타입 + HTTP 클라이언트 + 엔드포인트 + MSW 목 |
| `@ondo/shared` | ← `utils` + `hooks` | 순수 함수 + 도메인 무관 범용 훅 |
| `@ondo/config` | ← `eslint-config` + `typescript-config` | 린트 · TS · Prettier 설정 |

**함께 확정하는 불변 규칙 2개** (통합해도 이 둘만 지키면 구조가 무너지지 않는다):
1. `@ondo/ui`는 `@ondo/api`를 import 하지 않는다 — 컴포넌트에 도메인 지식 금지 (ESLint로 강제)
2. TanStack Query 훅은 **앱 안에만** 존재한다 — 공유는 "요청 방법"까지, "해석 방법"은 앱이 소유

## 대안

### A. 패키지 8개 (요구사항 그대로 매핑)
- 장점: 책임 경계가 이름으로 드러남. 팀·앱이 늘었을 때 그대로 확장됨. 업계 표준 형태
- 단점: 1인이 6개월간 8개의 설정·의존성·exports를 유지. 사용처 1곳뿐인 패키지가 생김 (`hooks`는 6개월간 범용 훅 10개 미만 예상)
- 탈락 이유: **비용은 즉시 발생하고 이득은 조건부 미래에 있다.** 그 미래(팀 확장, 외부 배포)가 6개월 안에 올 근거가 없다

### B. 패키지 없이 앱 2개 + 상대경로 공유
- 장점: 설정 비용 0
- 단점: 앱 간 참조는 빌드·배포 경계를 깨뜨린다. Vercel Root Directory 밖 파일 참조가 얽히고 `turbo-ignore` 판단도 부정확해짐
- 탈락 이유: 공유 코드가 70%인 두 앱에서 경계 없는 참조는 6개월 뒤 손댈 수 없게 된다

### C. 4개 통합 (채택)
- 통합 대상 4쌍이 모두 **"같은 사람이 같은 PR에서 함께 수정하는 것"**이라는 공통점을 가진다. 이건 패키지를 나누지 말아야 한다는 가장 강한 신호다

## 결과

**좋아지는 것**
- 관리 표면적 절반 — `package.json` 8개 → 4개, 의존성 업그레이드 확인 지점 절반
- 의존성 그래프가 3레이어로 단순해져 순환 참조 위험이 사실상 사라짐 (`shared` → `ui`/`api` → `apps`)
- 새 기능 작업 시 "이 코드를 어느 패키지에 둘까" 고민이 줄어든다
- 토큰 변경이 컴포넌트 변경과 한 PR에 담긴다 (`design-system`/`ui` 분리 시 두 패키지에 걸침)

**나빠지는 것 / 감수하는 비용**
- `@ondo/api`가 "타입 + 통신 + 목킹" 세 책임을 갖는다. 단일 책임 원칙 관점에서는 후퇴 — **의도적으로 감수한다.** 셋의 변경 이유가 전부 "API 스펙 변경"으로 동일하기 때문
- `@ondo/shared`는 성격상 잡동사니가 되기 쉽다 → 하위 디렉토리(`utils/`, `hooks/`)로 물리적 구분을 유지하고, 50파일을 넘으면 분리
- Turborepo 캐시 입도가 거칠어진다. 유틸 함수 1개 수정에도 `shared` 의존 태스크가 전부 재실행됨 (앱 2개 규모에선 체감 없음)
- 팀이 커졌을 때 패키지 단위 오너십을 부여하기 어렵다

**이 결정을 되돌려야 하는 신호**
- 앱이 4개를 넘을 때 → `ui`에서 `design-system` 분리 재검토
- `@ondo/shared`가 50파일을 넘을 때 → `utils` / `hooks` 분리
- FE 인원이 3명 이상이 되어 패키지별 오너십이 필요할 때 → 세분화
- `@ondo/api`의 코드젠 산출물 diff가 매 PR을 오염시킬 때 → `types` 분리

> **되돌리는 비용이 모두 낮다** (파일 이동 + import 경로 수정). 반대 방향(미리 8개로 나눠두기)은 6개월 내내 비용을 지불한다. 이 비대칭이 이 결정의 근거다.
