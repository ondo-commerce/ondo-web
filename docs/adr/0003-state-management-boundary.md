# ADR-0003: 서버 상태는 TanStack Query, 클라이언트 상태는 Zustand로 분리한다

- **Status**: Accepted
- **Date**: 2026-08-03
- **Decider**: Frontend 담당 (단독 결정)
- **관련**: [07 사전 결정](../07-pre-dev-decisions.md), ADR-0002

## 맥락

- 두 앱 모두 **화면 대부분이 서버 데이터 표시**다. 순수 클라이언트 상태(모달 열림, 사이드바 토글, 다단계 폼 진행)는 소수다.
- 프론트엔드 1명이 6개월간 두 앱을 만든다. 상태 관리에 쓰는 코드는 전부 기능 개발 시간을 깎아먹는다.
- 가장 흔한 사고 유형이 **"서버에서 받은 데이터를 전역 스토어에 복사해두고 동기화가 깨지는 것"**이다. 목록에서 수정한 값이 상세에 반영되지 않는 류의 버그가 여기서 나온다.
- App Router를 쓰므로 Server Component에서 가져온 데이터와 Client 캐시가 공존한다. 경계가 흐리면 데이터 출처가 두 곳이 된다.

## 결정

**상태를 출처 기준으로 두 종류로만 나누고, 각각 하나의 도구만 쓴다.**

| 종류 | 도구 | 예시 |
|---|---|---|
| 서버에서 온 것 (내가 소유하지 않음) | **TanStack Query v5** | 상품 목록, 주문 상세, 내 정보 |
| 브라우저에만 있는 것 (내가 소유) | **Zustand** | 인증 토큰(메모리), 사이드바 열림, 장바구니 로컬 초안 |
| 한 화면 안에서만 필요한 것 | **`useState`** | 입력값, 모달 open |
| URL로 표현되어야 하는 것 | **`useSearchParams`** | 필터, 페이지 번호, 검색어 |

**강제 규칙**
1. **서버 데이터를 Zustand에 복사하지 않는다.** Query 캐시가 유일한 원본
2. Zustand 스토어는 **최대 3개**로 제한 (`auth`, `ui`, 앱별 1개). 늘어나면 설계를 다시 본다
3. 필터·정렬·페이지는 **URL이 원본.** 상태로 들고 있지 않는다 (새로고침·공유·뒤로가기가 공짜로 동작)
4. queryKey는 팩토리로 관리 → [05](../05-api-contract.md#쿼리-훅-규칙)

## 대안

### A. Redux Toolkit + RTK Query 하나로 통합
- 장점: 도구 하나. RTK Query가 서버 상태도 처리
- 단점: 슬라이스·스토어·프로바이더 보일러플레이트가 1인 개발에서 순수 비용. 클라 상태가 몇 개 안 되는데 인프라가 과하다
- 탈락 이유: 우리가 필요한 전역 클라 상태는 사실상 **토큰 + UI 토글 2~3개**다. 여기에 Redux를 얹는 건 배보다 배꼽

### B. Context API만 사용
- 장점: 의존성 0
- 단점: 값이 바뀔 때 하위 트리 전체 리렌더. 캐시·재검증·중복요청 제거를 직접 구현해야 함
- 탈락 이유: 캐시 무효화와 낙관적 업데이트를 직접 만들면 **그것만으로 몇 주짜리 일**이다

### C. Server Component + Server Action만 사용 (클라 상태 관리 없음)
- 장점: 가장 적은 코드. Next.js 정공법
- 단점: 도매 어드민은 필터·정렬·인라인 편집이 많아 매 인터랙션마다 서버 왕복이면 체감이 나쁨
- 탈락 이유: **소매에는 부분 채택(상품 목록/상세는 SSR), 도매에는 부적합.** 전면 채택은 안 하되 소매에서는 이 방향을 쓴다

## 결과

**좋아지는 것**
- "이 상태를 어디에 둘까"를 매번 고민하지 않는다 → 출처만 보면 답이 나온다
- 캐시 무효화·로딩/에러 상태·중복 요청 제거를 라이브러리가 처리
- 서버 데이터 복사가 없으므로 **동기화 버그 유형 자체가 사라진다**
- 필터/페이지가 URL에 있어 새로고침·공유·뒤로가기가 별도 코드 없이 동작

**나빠지는 것 / 감수하는 비용**
- 라이브러리 2개를 익혀야 한다 (다만 둘 다 API 표면이 작다)
- Query의 `staleTime`/`gcTime` 개념을 이해하지 못하면 "왜 갱신이 안 되지" 류 혼란이 생긴다 → QueryClient 기본값을 한 곳에 두고 개별 훅에서 예외만 지정
- Server Component 데이터와 Client Query 캐시가 같은 리소스를 다룰 때 **경계를 명시적으로 지켜야 한다** (소매: 목록/상세는 SSR, 인터랙션 이후는 Query)

**이 결정을 되돌려야 하는 신호**
- Zustand 스토어가 5개를 넘고 스토어 간 의존이 생길 때 → 설계 재검토
- 서버 데이터를 스토어에 넣고 싶은 요구가 반복될 때 → 그 요구의 정체는 대개 "Query 사용법을 모르는 것"이므로 먼저 확인
- 실시간(웹소켓) 요구가 확정될 때 → 캐시 갱신 전략 재설계 필요
