# ADR-0001: 도매/소매 웹앱을 단일 모노레포(`ondo-web`)로 관리한다

- **Status**: Accepted
- **Date**: 2026-08-03
- **Decider**: Frontend 담당 (단독 결정 — FE 레포 구조는 FE 오너십)
- **관련**: [01 Repository 구조](../01-repository.md)

## 맥락

- 도매 판매자용 / 소매 구매자용 **웹 서비스 2개**를 만든다.
- **프론트엔드 개발자는 1명**, 기간은 6개월.
- 두 앱은 상품·주문·인증 도메인을 공유한다. 디자인 토큰과 기본 UI 요소도 공유된다.
- 배포는 Vercel. 백엔드는 별도 담당(2명)이 별도 레포에서 개발한다.
- 즉, 결정해야 할 것은 두 가지다: (1) 두 앱을 한 레포에 둘 것인가, (2) BE를 같은 레포에 둘 것인가.

## 결정

**도매 앱 + 소매 앱 + 공유 패키지를 `ondo-web` 단일 모노레포(pnpm workspace + Turborepo)로 관리한다.**
**백엔드는 포함하지 않는다.** FE-BE는 `openapi.yaml` 계약으로만 연결한다.

```
ondo-web/
├── apps/wholesale, apps/retail
└── packages/ui, api, utils, tailwind-config, eslint-config, tsconfig
```

Vercel 프로젝트는 2개로 나누고 Root Directory를 각각 지정, `turbo-ignore`로 변경된 앱만 빌드한다.

## 대안

### A. 앱별 레포 분리 (`ondo-wholesale`, `ondo-retail`, `ondo-ui`)
- 장점: 레포별 권한·CI가 독립적, 빌드 범위가 명확
- 단점: 공유 UI를 npm 패키지로 발행 → 버전 올림 → 두 앱에서 각각 갱신. 변경 1건에 PR 3개
- 탈락 이유: **FE가 1명이다.** 이 오버헤드를 나눠 질 사람이 없다. 공유 컴포넌트 하나 고치는 데 반나절이 든다

### B. FE + BE 통합 모노레포
- 장점: 타입을 소스 레벨에서 공유 가능, 전체 변경이 한 PR에 담김
- 단점: 서로 다른 런타임·CI가 한 레포에 섞이고, Turborepo 캐시가 BE 쪽에서 무의미해짐. 오너십이 다른 3명의 리뷰/릴리스 규칙을 하나로 강제해야 함
- 탈락 이유: 타입 공유 문제는 **OpenAPI 코드젠(ADR-0002)으로 이미 해결된다.** 통합할 유일한 근거가 사라졌다

## 결과

**좋아지는 것**
- 공유 컴포넌트·타입 변경이 **한 PR에서 두 앱에 원자적으로 반영**된다
- ESLint·TS·Prettier 설정이 하나. 1인이 관리하는 설정 표면적이 절반
- Turborepo 원격 캐시로 CI 시간 단축, `turbo-ignore`로 무관한 앱 빌드 제거
- 한 사람이 두 앱을 오가며 작업할 때 컨텍스트 전환 비용이 낮다

**나빠지는 것 / 감수하는 비용**
- 초기 세팅이 단일 앱보다 반나절 정도 더 든다 (workspace, turbo.json, Vercel Root Directory)
- 레포 하나가 커져 클론·설치 시간이 늘어난다
- Vercel 모노레포 설정을 잘못하면 두 앱이 매번 같이 빌드된다 → `turbo-ignore` 설정이 필수
- 한 앱의 lint 에러가 다른 앱 CI도 막을 수 있다 (task 필터링으로 완화)

**이 결정을 되돌려야 하는 신호**
- 두 앱의 공유 코드 비율이 **20% 아래로 떨어질 때** (= 사실상 다른 제품)
- 앱별로 배포 주기·릴리스 승인 주체가 완전히 갈릴 때
- FE 인원이 3명 이상으로 늘고 앱별로 팀이 분리될 때
