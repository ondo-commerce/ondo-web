# ADR 관리 방식 · P0

## ADR이란 / 왜 쓰나

**Architecture Decision Record** — "왜 이렇게 했는지"를 결정 시점에 남기는 1페이지 문서.

6개월 뒤 나 자신이나 멘토·심사위원이 **"왜 모노레포죠?", "왜 Redux 안 썼죠?"** 라고 물었을 때,
기억에 의존하지 않고 답할 수 있게 하는 게 목적이다. 특히 마에스트로처럼 **발표·심사가 있는 프로젝트에서 ADR은 그대로 발표 자료가 된다.**

> 부수 효과가 더 크다: **글로 못 쓰는 결정은 대개 근거가 없는 결정이다.** 쓰다 보면 잘못된 선택이 걸러진다.

## 언제 쓰나 — 판단 기준

> **"이 결정을 3개월 뒤에 되돌리려면 하루 이상 걸리나?"** → YES면 ADR을 쓴다.

| 쓴다 ✅ | 안 쓴다 ❌ |
|---|---|
| 레포·폴더 구조 | 변수명, 파일명 |
| 상태 관리 라이브러리 선택 | 아이콘 라이브러리 |
| API 계약 방식 (코드젠/목킹) | 특정 컴포넌트 구현 방식 |
| 인증·토큰 저장 위치 | 색상값 조정 |
| 렌더링 전략 (SSR/CSR 기준) | 유틸 함수 추가 |
| 주요 라이브러리 도입·제거 | 버전 패치 업그레이드 |
| **"안 하기로 한 것"** (GraphQL, Redux 등) | |

**"안 하기로 한 결정"도 ADR로 남긴다.** 3개월 뒤 누군가 "이거 왜 안 썼지?" 하고 다시 도입하려 할 때 시간을 아낀다.

### 1인 FE의 현실적 목표: **6개월간 ADR 8~12개.**
매주 쓰는 게 아니다. 그 정도면 충분하고, 20개가 넘으면 ADR을 쓰지 말아야 할 것까지 쓰고 있는 것이다.

## 어떻게 운영하나

### 워크플로

```
1. 결정이 필요한 상황 발생
2. docs/adr/0000-template.md 복사 → 다음 번호 부여, Status: Proposed
3. 대안 2개 이상을 실제로 써본다 (안 써보고 쓰는 ADR은 사후 정당화일 뿐)
4. PR로 올린다
   · FE 단독 결정 → 셀프 머지, Status: Accepted
   · 팀 영향 결정(인증·API·배포) → BE 1명 승인 후 머지
5. 관련 코드 PR 본문에 ADR 링크
```

### Status

| 상태 | 의미 |
|---|---|
| `Proposed` | 검토 중. 아직 코드에 반영하지 않음 |
| `Accepted` | 확정. 코드가 이걸 따른다 |
| `Superseded by ADR-00XX` | 다른 결정으로 대체됨 |
| `Deprecated` | 더 이상 유효하지 않음 (대체 결정 없음) |

**규칙: 기존 ADR을 수정하지 않는다.** 결정이 바뀌면 **새 ADR을 쓰고** 옛 것을 `Superseded`로 표시한다.
ADR은 "현재 상태"가 아니라 **"결정의 역사"**다. 덮어쓰면 왜 바뀌었는지가 사라진다.

### 분량

**1페이지. 길어야 A4 한 장.** 길어지면 아무도 안 읽고, 안 읽히면 쓰는 의미가 없다.
"대안" 섹션에 대안 2개, 각 3줄이면 충분하다.
