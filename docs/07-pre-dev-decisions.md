### A17. 렌더링 전략 — 화면별로 지금 정한다

나중에 바꾸면 데이터 페칭 코드를 전부 다시 쓴다.

| 화면 | 방식 | 이유 |
|---|---|---|
| 소매: 상품 목록/상세/검색 | **Server Component fetch** | SEO + 초기 로딩 |
| 소매: 장바구니/주문/마이페이지 | Client + Query | 로그인 필요, SEO 무관 |
| 도매: 전 화면 | **Client + Query** | 어드민, 인터랙션 위주 |

### A18. 환경변수

`.env.example`을 지금 커밋하고, `shared/config/env.ts`에서 zod로 검증한다 (누락 시 **빌드 실패**).

```bash
# .env.example
NEXT_PUBLIC_API_BASE_URL=https://api-dev.ondo.xxx
NEXT_PUBLIC_API_MOCK=true          # MSW 스위치
NEXT_PUBLIC_SENTRY_DSN=
# 서버 전용(NEXT_PUBLIC_ 없음)은 절대 클라이언트에서 import 하지 않는다
```
규칙: **`process.env` 직접 참조 금지.** 항상 `env.ts` 경유 → 오타·누락이 런타임이 아니라 빌드에서 잡힌다.

## B. 팀 합의가 필요한 것

킥오프 회의 1회(90분) 안건. 이건 내가 정할 수 없다. **회의 전에 아래 초안을 미리 보내고, 회의에서는 확정만 한다.**

### B1. 인증 — 가장 비싸고 가장 자주 미뤄지는 결정 🔴

| 항목 | 내 제안 | 확정 |
|---|---|---|
| 토큰 종류 | Access(짧음, 30분) + Refresh(길음, 2주) | ⬜ |
| Access 전달 | `Authorization: Bearer` 헤더 | ⬜ |
| Access 저장 | **메모리(JS 변수)** — localStorage는 XSS에 그대로 노출 | ⬜ |
| Refresh 저장 | **httpOnly + Secure + SameSite 쿠키** (BE가 발급) | ⬜ |
| 갱신 흐름 | 401 → `/auth/refresh` 1회 재시도 → 실패 시 로그인 이동 | ⬜ |
| 동시 401 | 갱신 요청 1개로 합치고 나머지는 대기 (큐잉) | ⬜ |
| 로그인 주체 | 도매/소매 계정 체계가 분리인가 통합인가 | ⬜ |
| 소셜 로그인 | MVP 범위인가 | ⬜ |

> **"일단 localStorage에 넣고 나중에 바꾸자"를 하면 안 된다.** 저장 위치가 바뀌면 미들웨어·SSR 인증·인터셉터를 전부 다시 쓴다.

### B2. 에러 / 페이지네이션 / 상태값
→ [05](05-api-contract.md#be에-요청할-것)의 포맷을 그대로 제안. 각 ⬜ 확정.
추가로 **enum 값 표기**를 합의한다: 주문상태를 `PENDING`(문자열)로 줄지 `1`(숫자)로 줄지. 숫자면 FE가 매핑표를 들고 있어야 하고 디버깅이 지옥이 된다 → **문자열 SCREAMING_SNAKE 권장.**

### B3. 도메인 용어 사전 🔴
→ [06](06-docs-structure.md#용어-사전을-p1로-두는-이유). API 필드명이 여기서 나오므로 **API 설계보다 먼저** 확정.

### B4. 파일 업로드
| 항목 | 제안 | 확정 |
|---|---|---|
| 방식 | S3 presigned URL (BE가 URL 발급, FE가 직접 PUT) | ⬜ |
| 제약 | 최대 5MB, jpg/png/webp | ⬜ |
| 리사이즈 | 업로드 전 클라이언트 압축 여부 | ⬜ |
| 이미지 도메인 | `next.config` remotePatterns에 넣을 CDN 도메인 | ⬜ |

### B5. 배포·환경
| 항목 | 제안 | 확정 |
|---|---|---|
| 환경 수 | local / dev(스테이징) / prod 3개 | ⬜ |
| FE-BE 매핑 | `dev` 브랜치 ↔ `api-dev`, `main` ↔ `api` | ⬜ |
| 배포 순서 | breaking change는 BE 먼저 | ⬜ |
| 데모 시점 | 중간발표 D-3에 `main` 프리즈 | ⬜ |

### B6. MVP 범위 확정 — In / Out
"MVP는 이미 정의되어 있음"이라도 **Out 목록이 문서화되어 있지 않으면 정의된 게 아니다.**
회의에서 "MVP에 안 넣는 것" 리스트를 명시적으로 받아낸다. 이게 6개월 일정을 지키는 가장 강력한 장치다.

## C. 지금 결정하지 않는다 (명시적 보류)

| 항목 | 언제 |
|---|---|
| 다크모드 | 토큰을 CSS 변수로 깔아뒀으므로 나중에 싸게 추가 가능 |
| i18n | 요구 확정 후. 지금 하면 전 문자열에 키를 달아야 함 |
| 실시간(웹소켓) | 폴링으로 시작. 요구가 확정되면 교체 |
| 무한스크롤 vs 페이지네이션 | 소매 상품 목록 디자인 확정 후 (커서 API 필요 여부가 달림) |
| 접근성 등급 | WCAG AA 전면 준수는 무리. 포커스·label·대비 3가지만 지킨다 |
| PWA / 푸시 | MVP 이후 |

## 킥오프 회의 아젠다 (90분, 그대로 사용)

| 시간 | 안건 | 산출물 |
|---|---|---|
| 0~20분 | **도메인 용어 사전** 확정 | Notion 표 |
| 20~40분 | **인증 전략** (B1) 확정 | ADR-0003 |
| 40~60분 | 에러 포맷 · 페이지네이션 · enum 표기 (B2) | openapi 규약 |
| 60~75분 | 환경/배포/도메인 (B5) | 환경변수 목록 |
| 75~90분 | **MVP Out 목록** (B6) | 안 만드는 것 리스트 |

> 폴더 구조·상태관리·컴포넌트 전략은 **회의 안건이 아니다.** FE 담당인 내가 정하고 통보한다. 회의 시간은 나 혼자 못 정하는 것에만 쓴다.
