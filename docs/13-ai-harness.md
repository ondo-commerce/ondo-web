# AI 개발 하네스 — 누가 무엇을 정하나

이 레포의 화면은 Claude 에이전트와 Codex가 만들고 사람이 결정한다. 에이전트 정의와 훅은 개인 도구로 관리하며 레포 밖의 `~/.claude/`에 둔다. 레포 안의 `.claude/`는 Git 추적에서 제외한다. 이 문서는 그 구조를 레포 안에서 읽을 수 있게 옮긴 것이다. 로컬 하네스 README의 구조가 바뀌면 이 문서도 같이 고친다. 2026-11-08 멘토링(과제 전형은 "일하는 방식"을 본다)을 반영해 정리했다.

## 1. 흐름

```
기획(Story, AC) → 디자인(방향안 → 와이어프레임) → Codex 비판 → ★G1 사람 승인
→ 계약(OpenAPI 초안 + 목) → ★G2 사람 승인
→ 구현 + 테스트(이슈 1개 = 커밋 1개) → Codex 리뷰 ∥ QA(브라우저, e2e)
→ ★G3 결함 처리 결정 → 보고
```

사람은 세 게이트에서 승인과 결함 처리를 결정하고, 작업 중 우선순위 충돌이나 에이전트 질문에도 답한다. 에이전트는 각 단계의 산출물을 만들고 다음 단계가 그것을 읽는다.

## 2. 역할과 모델

| 역할 | 누가 | 비고 |
|---|---|---|
| 기획, 디자인, 구현+테스트, QA | Claude 에이전트 4종 | 각자 "하지 않는 것"이 정해져 있다. 구현은 스펙을 정하지 않고, QA는 코드를 고치지 않는다 |
| 레퍼런스 수집, 보고 집계, 이슈 생성 스크립트 | Claude, 작은 모델 | 정확도보다 처리량이 중요한 일 |
| 기획 비판, 코드 리뷰, 기획과 구현이 어긋난 곳 점검 | Codex | 만든 쪽과 다른 모델이 본다 |
| 게이트 결정, 결함 처리 방향, 우선순위 충돌 | 사람 | 아래 4절 |

같은 이슈의 검증이 두 번 실패하면 그 이슈를 맡은 에이전트만 더 큰 모델로 다시 실행한다.

## 3. 우선순위

화면별 우선순위와 예외는 `CLAUDE.md`의 우선순위 절을 따른다. 원본은 거기 하나이고 여기 반복하지 않는다. 에이전트는 그 순서로 짜고, 항목 중 하나를 포기해야 하면 사람에게 묻는다.

## 4. 결함과 결정의 기록

**findings.jsonl** — 결함 1건 = JSON 한 줄. 심각도 P0(업무 불가) / P1(자주 만남) / P2(드묾) / P3(외관). 회차의 모든 줄에 `exit`이 채워져야 끝난다.

| `exit` | 뜻 |
|---|---|
| `fixed:<커밋>` | 같은 PR에서 고쳤다 (P0, P1은 여기로) |
| `issue:#<번호>` | GitHub 이슈를 실제로 만들었다 |
| `guard:<장치>` | 재발 방지 장치(린트 규칙, 컴포넌트 API, 테스트)를 넣었다 |
| `accept:<이유>` | 안 고친다. 이유를 적는다 |

결함을 문서에 적는 것으로 처리를 끝내지 않는다. 그렇게 남긴 결함은 이전 회차에서 후속 처리 없이 묻혔다.

**decisions.md** — 회차마다 하나. AI가 정하지 못해서 사람이 정한 것만 적는다. 게이트 답, 에이전트가 올린 질문(정렬 동률, 빈 상태, 권한 없는 사용자), 리뷰 P2와 P3를 반영하지 않은 이유. 형식은 `| 날짜 | 출처 | 질문 | 결정 | 이유 |`.

**ADR** — 아키텍처 결정은 [`adr/`](adr/).

## 5. 사람이 하는 일 (면접에서 묻는 질문에 대한 이 레포의 답)

1. 리뷰 지적 중 반영할 것과 안 할 것을 정한다. P0, P1은 무조건, P2와 P3는 이유를 적고 고른다.
2. AI가 코드만 보고는 정할 수 없는 것을 정한다. 어떤 값을 우선하나, 값이 틀리는 것과 응답이 느린 것 중 무엇을 참나 같은 것.
3. 영업의 말("재고 문의에 자동으로 답해라")을 Story와 AC, 이슈 단위로 쪼갠다. 이 쪼개기까지 에이전트가 초안을 내지만 승인은 사람이 한다.
