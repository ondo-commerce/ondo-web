# AI 개발 하네스 — 누가 무엇을 정하나

이 레포의 화면은 Claude 에이전트와 Codex가 만들고 사람이 결정한다. 에이전트 정의와 훅은 개인 도구라 레포 밖(`~/.claude/`, `.claude/`는 gitignore)에 있다. 이 문서는 그 구조를 레포 안에서 읽을 수 있게 옮긴 것이다. 2026-11-08 멘토링(과제 전형은 "일하는 방식"을 본다)을 반영해 정리했다.

## 1. 흐름

```
기획(Story, AC) → 디자인(방향안 → 와이어프레임) → Codex 비판 → ★G1 사람 승인
→ 계약(OpenAPI 초안 + 목) → ★G2 사람 승인
→ 구현 + 테스트(이슈 1개 = 커밋 1개) → Codex 리뷰 ∥ QA(브라우저, e2e)
→ ★G3 결함 처리 결정 → 보고
```

게이트 3곳에서만 사람이 나온다. 나머지는 에이전트가 산출물을 만들고 다음 단계가 그걸 읽는다.

## 2. 역할과 모델

| 역할 | 누가 | 비고 |
|---|---|---|
| 기획, 디자인, 구현+테스트, QA | Claude 에이전트 4종 (Opus) | 각자 "하지 않는 것"이 정의돼 있다. 구현은 스펙을 정하지 않고, QA는 코드를 고치지 않는다 |
| 레퍼런스 수집, 보고 집계, 이슈 생성 스크립트 | Claude (Haiku) | 정확도보다 양이 많은 일 |
| 기획 비판, 코드 리뷰, 기획과 구현의 어긋남 점검 | Codex | 같은 모델이 쓰고 같은 모델이 리뷰하는 걸 피한다 |
| 게이트 결정, 결함 처리 방향, 우선순위 충돌 | 사람 | 아래 4절 |

승급 규칙: Opus 에이전트가 같은 이슈에서 검증을 두 번 못 넘기면 그 이슈만 상위 모델로 다시 부른다.

## 3. 우선순위 — 정합성 > 성능 > 유지보수성

`CLAUDE.md`의 같은 절이 원본이다. 도매는 재고와 정산이라 항상 정합성이 먼저. 소매는 탐색 화면은 성능, 주문과 재고가 걸리는 화면은 정합성. 에이전트는 이 순서로 짜고, 둘 중 하나를 포기해야 하면 사람에게 묻는다.

## 4. 결함과 결정의 기록

**findings.jsonl** — 결함 1건 = JSON 한 줄. 심각도 P0(업무 불가) / P1(자주 만남) / P2(드묾) / P3(외관). 회차의 모든 줄에 `exit`이 채워져야 끝난다.

| `exit` | 뜻 |
|---|---|
| `fixed:<커밋>` | 같은 PR에서 고쳤다 (P0, P1은 여기로) |
| `issue:#<번호>` | GitHub 이슈를 실제로 만들었다 |
| `guard:<장치>` | 재발 방지 장치(린트 규칙, 컴포넌트 API, 테스트)를 넣었다 |
| `accept:<이유>` | 안 고친다. 이유를 적는다 |

"문서에만 남김"은 없다. 그게 결함이 죽는 경로였다.

**decisions.md** — 회차마다 하나. AI가 정하지 못해서 사람이 정한 것만 적는다. 게이트 답, 에이전트가 올린 질문(정렬 동률, 빈 상태, 권한 없는 사용자), 리뷰 P2와 P3를 반영하지 않은 이유. 형식은 `| 날짜 | 출처 | 질문 | 결정 | 이유 |`.

**ADR** — 아키텍처 결정은 [`adr/`](adr/).

## 5. 사람이 하는 일 (면접에서 묻는 질문에 대한 이 레포의 답)

1. 리뷰 지적 중 반영할 것과 안 할 것을 정한다. P0, P1은 무조건, P2와 P3는 이유를 적고 고른다.
2. AI가 비즈니스만으로 결정할 수 없는 것(어떤 값을 우선하나, 틀린 값과 느린 값 중 뭘 참나)을 정한다.
3. 영업의 말("재고 문의에 자동으로 답해라")을 Story와 AC, 이슈 단위로 쪼갠다. 이 쪼개기까지 에이전트가 초안을 내지만 승인은 사람이 한다.
